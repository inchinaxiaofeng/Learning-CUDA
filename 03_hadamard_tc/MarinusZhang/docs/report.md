# 作业 03：Hadamard 变换加速（Tensor Core）实现报告

> 骨架文件，随里程碑推进补全；M2（寄存器蝶形 baseline）与 M3（Tensor Core GEMM）已落地。

## 1. 任务理解

沿最后一维对 `[B, S, H, D]` 做 Hadamard 变换，D 为 2 的幂；要求 FP16 绝对误差 < 1e-2、
BF16 < 5e-2，并与量化算子融合。详见 `03_hadamard_tc/README.md`。

## 2. 实现思路

### 2.1 变换约定（已与参考实现对齐）

做法：clone `Dao-AILab/fast-hadamard-transform`，先读源码把口径定下来，再编译安装它的 CUDA
扩展做数值对拍。

结论：

- 该库把缩放作为参数传入 kernel（`params.scale`），在写回时统一相乘；其 README 与自带测试
  统一取 `scale = 1/sqrt(dim)`，并声明等价于 `F.linear(x, scipy.linalg.hadamard(dim)) * scale`。
- 所以本项目的 `y = H_d x / sqrt(d)`（Sylvester 构造、自然顺序输出）与参考实现一致，不需要
  额外的归一化修正或输出置换。
- 该库对非 2 的幂尺寸内部补零到下一个 2 的幂；本项目按题面只支持 2 的幂。

### 2.2 非 Tensor Core baseline（M2）

实现位于 `src/hadamard_gpu.cu`，核心是把 `[B,S,H,D]` 展平成 `M = B·S·H` 行、行长 `D` 的二维
数组，再做蝶形 FWHT。

- **线程映射**：一行由同一 warp 内的 T 个线程协作，线程 `lane` 连续持有 `E = D / T` 个元素。
  E 以 8 为优选值（fp16/bf16 下正好一个 128-bit 向量）；`D > 8·32` 时改为增大 E 而不是 T，
  因为 shuffle 的分组不能跨 warp。`d = 2` 退化为 T = 1、E = 2。
- **蝶形**：第 `s` 级步长 `len = 2^s`。`len < E` 时配对的两个下标落在同一线程的寄存器里
  （线程持有的块按 E 对齐，异或不会跨块），直接寄存器加减；`len >= E` 时配对线程为
  `lane ^ (len / E)`、元素下标不变，用一次 `__shfl_xor_sync` 交换即可，符号折进求和
  （`v = sign·v + other`）。
- **零 shared memory**：上面两级合起来覆盖全部 `log2(D)` 级，所以 kernel 不碰 shared memory、
  不需要 `__syncthreads()`，一行只过一遍显存（一次读、一次写），理论上限就是 memcpy。
- **精度**：全程 FP32，仅在写回时按目标精度舍入一次；`1/sqrt(D)` 折进 epilogue，避免每级都
  引入舍入误差（否则半精度中间量的误差会直接吃掉 1e-2 的容差预算）。
- **访存**：按每线程 run 宽度选择 16/8/4/2 字节向量；行内 T 个线程连续访存，天然完全合并。
- **尾部处理**：最后一块中越界的线程不提前 return（否则 shuffle 的 mask 与配对会失效），
  而是钳到最后一个有效行继续计算、只跳过写回。
- **launch 粒度**：以每 SM 约 8 个 block 为目标反推 block 持有多少行，向上取整到整 warp，
  上限 256 线程，兼顾小 shape（行数少）与大 shape 的并行度。
- **支持范围**：`head_dim` 为 2 的幂且不超过 1024；其余尺寸返回 `false`，harness 报 SKIP。

### 2.3 Tensor Core 主实现（M3）

同样在 `src/hadamard_gpu.cu`（`tc_fwht_kernel`），把问题写成

```
Y (M×D) = X (M×D) · H_D (D×D)
```

的 tiled WMMA GEMM：A 操作数是激活，B 操作数是 ±1 常量矩阵，K = D 按 16 切分，
累加器全程 FP32，`1/sqrt(D)` 放在 epilogue。

**不存 D×D 矩阵。** Sylvester 构造满足

```
H_d[(i1,i0),(j1,j0)] = H_{d/16}[i1,j1] · H_16[i0,j0],   i = 16·i1 + i0
```

因为 `H_n[i,j] = (-1)^popcount(i&j)`，而 `i1` 与 `i0` 的比特不重叠。于是任意
(K tile, N tile) 需要的 B 分块只可能是 `+H_16` 或 `-H_16`，符号由
`(-1)^popcount(k_tile & n_tile)` 决定。收益：

- shared memory 只需要常驻两个 16×16 的 tile（共 1 KiB），**与 D 无关**。D = 512 若直接
  存 `H_d` 要 512 KiB，远超单 SM 的 100 KiB，所以这个技巧是必需的而不是可选优化。
- 每个 mma 都是满密度的 `m16n16k16`，没有为稀疏结构浪费算力。
- 两个符号变体都常驻寄存器，B 在 K 循环里零访存。
- d 的适用范围顺带放宽（smem 只需 16 行 × D，M2 的寄存器方案受限于每线程能装多少）。

写 kernel 之前先用一个仓库外的 host 程序验证了这条分块公式：d = 16…1024 逐元素与递归
构造的 `H_d` 比对（1,398,016 次检查全部相等），并用分块累加复算 `H_d x`，与显式 matmul
完全一致。这一步不能省——公式错了 kernel 里的 bug 会非常难查。

**线程映射与 tile 循环。** 一个 block 负责 16 行 × `kCols = min(D, 256)` 列，每个 warp
负责其中 `kCols / kWarps` 列并跑完整的 K = D 循环；D > 256 时再按列切成 2~4 个 block。
16 行 × D 的激活块先 staging 进 shared memory，行距取 `D + 8`：若行距正好是 128 B 的整数
倍，16 行会落在同一组 bank 上，`load_matrix_sync` 会退化。

**epilogue。** WMMA 的累加器片段是 FP32，而 `store_matrix_sync` 只能写与片段同类型的
buffer，输出却是 fp16/bf16，所以片段先落到 FP32 shared memory（与 A staging 共用同一块
buffer，中间用 `__syncthreads()` 隔开），再由线程按 16 B 向量读回、乘 `1/sqrt(D)`、舍入到
目标精度写出。行方向的越界线程在 staging 阶段钳到最后一个有效行、在写回阶段被掩掉，
因此 `rows = 1` 这类用例不需要特判。

**支持范围。** `D ≥ 16` 走 TC；`D ∈ {2,4,8}` 无法满足 `m16n16k16` 的 K ≥ 16，直接转调
M2 的蝶形实现（两条路径的精度口径一致，回落不影响对拍结论）。

## 3. 优化历程与踩坑

### 3.1 设计取舍：直接落地寄存器方案

原计划按「v0 逐级 shared memory 蝶形 → v1 向量化访存 → v2 shuffle 换 len < 32 → v3 每线程多元素」
的阶梯实现。读了参考实现的源码后确认：对本作业的 `D ≤ 512`，一行的全部数据在 32 个线程的
寄存器里就能装下（`32 × 8 × 2 B = 512 B`），于是 `len < E` 用寄存器加减、`len ≥ E` 用 warp
shuffle 的组合可以覆盖全部蝶形级次，根本不需要 shared memory。因此直接落地了这一版，
把 smem 版本留给 M3 里可能出现的跨 warp 交换场景。收益体现在实测上：DRAM 受限的大 shape
达到 943 GB/s（理论峰值的 93.6%），kernel 时间已经贴近 memcpy 这一上限（见第 4 节）。

### 3.2 踩坑 1：参考实现的越界 bug（M1）

CPU 参考里的 `build_sylvester` 用元素个数 `n·n` 当作矩阵维度来判断何时退出展开循环，
`d > 2` 时索引远远越过 buffer：`d = 128` 的最大误差 > 1e17、`d = 256` 直接段错误，而蝶形
参考实现却是对的。定位手法：利用解析性质「全 1 输入经 `y = H x / sqrt(d)` 应只有第 0 个
元素为 `sqrt(d)`、其余为 0」，一次就断定问题出在 matmul 参考而不是蝶形实现。修复后
`d = 2 … 512` 的两套参考实现互相吻合到 1e-6。

### 3.3 踩坑 2：host-only 的转换函数

`TypeTraits::to_float/from_float` 原本只在 host 侧（WMMA 探针）使用，kernel 里调用后报
`calling a __host__ function from a __device__ function`。补上 `__host__ __device__` 后
host/device 两侧共用同一套 fp16/bf16 转换。

### 3.4 踩坑 3：benchmark 带宽超过 HBM 峰值

首次实测小 shape 得到 1383–2694 GB/s，超过 4090 D 的 1008 GB/s 理论峰值。原因是 benchmark
对同一块 0.4–16 MiB 的张量重复 50 次迭代，输入输出全部落在 72 MiB 的 L2 里，测到的是 L2
带宽。核实手段：另写一个仓库外的临时程序，用 256 MiB 流量的大 shape 复测，得到 DRAM 受限的
943 GB/s；随后把该大 shape 加进 `bench_hadamard.cu`，让 benchmark 同时覆盖 L2 与 DRAM 两种
情形，并在输出里注明哪一行是 DRAM-bound。

### 3.5 踩坑 4：常量矩阵只被填了一半

`H_16` 的 256 个元素最初写成 `if (tid < 256) { ... }`，但 block 只有 32~128 个线程，
于是只有前 `blockDim.x` 个元素被写入，其余保持 shared memory 的初值 0。d = 16 时只有
`H_16` 的前 2 行非零，结果退化成「只对前两个输入做变换」，输出列呈现周期 2 的假象；
d = 64/128 时是周期 8，正是前 8 行非零。

定位手法值得记下来：不要盯误差量级，而是**把 kernel 实际作用的矩阵读出来**——用
one-hot 输入 `e_i` 跑 `rows = 1` 的用例，输出就是该矩阵的第 i 行。一次运行就看清楚
第 0、1 行正确、第 2 行起全 0，直接指向常量填充而不是 tiling/符号逻辑。改成
`for (v = tid; v < 256; v += blockDim.x)` 后所有尺寸回到 fp16 舍入水平（≤ 5e-4）。

### 3.6 踩坑 5：分支 vs 选择——fp16 被谓词化 HMMA 拖慢 1.5×

符号选择最初写成带分支的形式：

```
if (sign) mma(acc, fa, fb_neg, acc);
else      mma(acc, fa, fb_pos, acc);
```

结果是同一个 kernel、同样的 shape，bf16 比 fp16 快 1.5 倍，而且多次运行稳定（不是时钟
假象）。先排除了硬件差异：仓库外的纯 mma 微基准（fragment 常驻寄存器、无访存）测得两种
精度的裸吞吐相同（147.0 vs 146.7 TFLOPS，见第 4 节）。

dump SASS 后原因很清楚：bf16 实例编译出 8 条无谓词的 `HMMA.16816.F32.BF16`，fp16 实例
却是**两套被 `@!P0` 谓词化的 HMMA（共 16 条）加 10 条 WARPSYNC**——nvcc 把两个分支都
发射出来，并在每次谓词化 mma 后插入 warp 同步，MMA 的发射槽因此直接翻倍。

把分支改成分支无关的选择（先 `fb = sign ? fb_pos : fb_neg` 再 mma）后，fp16 与 bf16 的
数字并齐，L2 受限的 shape 提升 1.5~1.7×（621 → 914 GB/s、946 → 1581 GB/s）。这也是本
里程碑里性价比最高的一个改动。

## 4. 性能指标与分析

RTX 4090 D（sm_89，114 SM，1008 GB/s HBM 峰值），`hw_bench`，50 次迭代取均值，
有效带宽按「一次读 + 一次写」计；fp16 与 bf16 的耗时差异在 1% 以内，下表以 fp16 列 ms、
bf16 只列带宽。L2 常驻的几行逐次运行有 2~3% 抖动。

先给出两条路线的算术强度。M2 每行 `D·log2(D)` 次加减、每元素读一个、写一个，
算术强度约 `log2(D)/2 ≈ 3.5 flops/byte`；M3 每行 `2D²` 次 MAC，强度为 `D/2`。平台的机器
平衡点由实测的裸 mma 峰值给出：仓库外的微基准（fragment 常驻寄存器、无访存、4 条独立
累加器链）测得 **147.0 TFLOPS（fp16 → fp32 累加）** 与 **146.7 TFLOPS（bf16 → fp32 累加）**
——两种精度的 Tensor Core 吞吐实际上相同。对 1008 GB/s 的 HBM 就是 **146 flops/byte**，
对实测 2.5–2.7 TB/s 的 L2 只有 **~50 flops/byte**。

| shape (B,S,H,D) | D | 流量 | CPU fp32 | M2 fp16 | M2 带宽 | M3 fp16 | M3 带宽 | M3/M2 | M3 bf16 带宽 |
|---|---|---|---|---|---|---|---|---|---|
| [1,128,12,64] | 64 | 0.4 MiB | 0.3024 ms | 0.0026 ms | 154 GB/s | 0.0025 ms | 157 GB/s | 0.96× | 157 GB/s |
| [2,256,16,128] | 128 | 4 MiB | 3.2696 ms | 0.0030 ms | 1422 GB/s | 0.0046 ms | 914 GB/s | 1.53× | 883 GB/s |
| [1,512,8,256] | 256 | 4 MiB | 3.3861 ms | 0.0032 ms | 1313 GB/s | 0.0079 ms | 532 GB/s | 2.47× | 520 GB/s |
| [4,512,16,128] | 128 | 16 MiB | 13.5821 ms | 0.0062 ms | 2704 GB/s | 0.0106 ms | 1582 GB/s | 1.71× | 1578 GB/s |
| [1,4096,12,64] | 64 | 12 MiB | 9.8621 ms | 0.0051 ms | 2487 GB/s | 0.0088 ms | 1426 GB/s | 1.73× | 1359 GB/s |
| [8,4096,16,128] | 128 | 256 MiB | 234.4720 ms | 0.2845 ms | 943 GB/s | 0.2862 ms | 938 GB/s | 1.006× | 939 GB/s |

分析：

- **前五行的工作集（≤ 16 MiB）在 50 次迭代中一直驻留在 72 MiB L2**，报出的是 L2 带宽，
  数值高于 HBM 峰值属于正常现象；真正衡量 kernel 上限的是最后一行。
- **DRAM 受限的行两者打平**：256 MiB 流量下 M2 为 943 GB/s（理论峰值的 93.6%），M3 为
  938 GB/s，差距 0.6%。这一行的算术强度是 `D/2 = 64` flops/byte，仍低于 DRAM 的 146，
  所以 M3 只要把多余流量控住也能跑在访存上限上；实测正好如此，与预测一致。相对 CPU fp32
  参考，这两条路径分别加速 824× 与 819×。
- **L2 常驻的行 M3 反而慢 1.5~2.5×**：这些 shape 的算术强度高于 L2 的 ~50 flops/byte，
  变成计算受限，而 M3 每行的 MAC 数是 `D²` 量级（相对 M2 的 `D·log2(D)` 多出 `D/log2(D)` 倍，
  D = 128 时约 18×）。D = 128 的 16 MiB 行是差距最小的一档（1.71×），因为它的数据量每个
  block 最大、固定开销摊得最薄；D = 256 的 4 MiB 行最慢（2.47×），因为每行 MAC 数再翻倍而
  数据量相同。
- **D = 64 的行（强度 32 < L2 的 50）按理应该是访存受限，实测仍慢 1.7×**，这是每 block
  固定开销在作祟：16 行 × 64 列的 tile 只有 4 KiB 流量，却要做 prologue（`H_16` 构造、A
  staging、两次 `__syncthreads()`）与 epilogue，这部分开销摊不薄。
- **达到的 mma 峰值比例**：`[4,512,16,128]` 为 101 TFLOPS = 峰值的 69%，`[2,256,16,128]`
  为 58 TFLOPS（40%），`[1,4096,12,64]` 为 46 TFLOPS（31%），大 shape 为 60 TFLOPS（41%，
  但这一行本来就是访存受限，938 GB/s 已达 HBM 峰值的 93%）。值得注意的是即使是最优的一行
  也没打满——这与上面的固定开销是同一件事。
- **fp16 与 bf16 一致**（差异 < 1%），与微基准的裸吞吐结论一致；早期 fp16 慢 1.5× 的
  现象见 §3.6，是代码生成问题而不是数据格式问题。
- 最小的 shape（0.4 MiB）两者都在 150 GB/s 上下：2.5 µs 里大部分是 kernel 启动与尾部延迟，
  不是带宽问题；这类 shape 的优化方向是减少 launch 与尾部开销，而不是改访存或蝶形。

（待补：M4 融合量化路线与上述两路的对比；nsys 时间线与代码级计时的侧证。本容器没有 ncu，
`nvprof` 也不支持 Ada，因此缺少 DRAM 吞吐 / occupancy / stall 的硬件计数。）

## 5. 正确性验证

- **对拍口径**：输入先量化到目标精度，参考值在该量化输入上计算，因此误差只反映 kernel 误差，
  不混入输入量化误差。
- **CPU 参考自洽**：Sylvester 显式 matmul 与蝶形 FWHT 两条独立实现互相吻合，
  `d = 2/64/128/256/512` 最大差 2e-6；正交性检查（连续做两次变换应回到原值）对全部尺寸
  通过，可捕获符号、顺序与归一化错误。
- **GPU 对拍**：`hw_tests` 中 20 个 GPU 用例（fp16/bf16 × `d = 2/64/128/256/512` × M2/TC 两条路径，
  其中 `d = 2` 由 TC 路径转调 M2）全部 PASS。实测最大绝对误差：fp16 ≤ 7.4e-4（门槛 1e-2），
  bf16 ≤ 7.6e-3（门槛 5e-2），余量均在 10 倍以上。
- **两条路径相互印证**：TC 用例与 M2 用例的最大误差逐位相同，说明两者都是 FP32 累加、
  只在写回时舍入一次；B 操作数的 ±1 在 fp16/bf16 下精确，所以差异只来自累加顺序，
  完全落在最后一次舍入之内。
- **TC 路径的额外自查**：用 one-hot 输入把 kernel 实际作用的矩阵读出来与 `H_16` 逐元素比对
  （做法见 §3.5）。这比只看误差量级更容易发现结构性错误，建议保留为回归手段。
- **与官方实现对拍**：把官方 `fast_hadamard_transform` kernel 消费的同一份 fp16/bf16 输入喂给
  我们的 kernel，`d = 2/64/128/256/512` 全部逐元素 **bit-exact（max|diff| = 0）**。这说明两者的
  中间精度与舍入方式也完全一致（双方都是 FP32 累加、只在写回时舍入一次）。

（待补：M4 融合量化 vs 两段式的一致性验证）

## 6. 未来工作

- **radix-16 hybrid（下一步最有价值的方向）**：M3 现在做的是**完整** GEMM，每行 `D²` 次 MAC；
  若只把「16 点 radix 级」交给 Tensor Core（该级在 16×16×16 上就是满密度的 H_16），
  剩下的 `D/16` 点变换仍用 M2 的蝶形（需要 strided 版本或经 smem 转置），算术强度可以从
  `D/2` 压回 ~5 flops/byte，即回到与 M2 相同的访存受限区间。这是目前看来唯一能让 Tensor Core
  路线在计算受限档位（D ≥ 128 的 L2 场景、D ≥ 512 的 DRAM 场景）追平或反超蝶形的方案。
- **扩大块粒度**：现在一个 block 只有 16 行，prologue 与 epilogue 的固定开销摊不薄，实测只到
  裸 mma 峰值的 40~69%。改成 32/64 行一块、A staging 双缓冲，是收窄这部分差距的直接手段；
  相应地也能修掉 D = 64 那一档的异常。
- **列块的重复 staging**：D > 256 时每个列块都会重新 staging 整行激活，D 较大时可以改成
  按 K 分块或让同一 block 覆盖全部列。
- **M4 融合量化**：FP8 E4M3 per-token 量化的 epilogue，验证与「先变换后量化」逐元素一致。
- **更大的 head_dim**：超过 1024 后每线程寄存器装不下一行，需要跨 warp 的 shared memory
  交换（参考实现的做法）或分块策略。
- **非 2 的幂**：按参考实现补零到下一个 2 的幂。
- **小 shape 的 launch 开销**：`[1,128,12,64]` 这类只有 2 µs 的场景，可考虑合并多行/多次调用、
  持久化 kernel 或 CUDA Graph。
- **profiling**：本容器没有 `ncu`（`nvprof` 不支持 Ada），只有 `nsys`。后续用 `nsys` 时间线 +
  代码级事件计时侧证 §4 的结论，或在有 ncu 的机器上补采几个关键 shape 的 DRAM 吞吐 /
  occupancy / stall 计数。
